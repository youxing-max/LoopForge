# 大型项目实战指南（0 → 1 从零开发）

> 前面的文档讲的是「一个需求」怎么走完 Loop。这份讲的是**几十上百个需求、跨月、多人**的项目怎么用。
> 前置：先读 README、`goal-template.md`、`role-permission-matrix.md`。

---

## 一、单需求 Loop 撑不住大型项目的地方

| 单需求假设 | 大型项目现实 | 后果 |
|:--|:--|:--|
| 一份 `docs/loopforge/srs/<需求>.md` | 上百条需求，几十份文档 | SRS 无法单文件管理，编号会撞 |
| 一次跑完 5 个 Stage | 需求分批交付，跨周跨月 | 没有"批次"概念，无法并行 |
| 一个验证组一个 runner | 前后端/DB/基础设施多个子系统 | 单 runner 跑全量要几十分钟 |
| `docs/loopforge/loop-status.md` 一张表 | 多批次并行，状态互相覆盖 | 状态表打架 |
| 上下文里记着当前进度 | 跨会话、跨人 | 上下文一丢全部重来 |
| 交付一次就结束 | 持续迭代，需求会变 | 没有变更流程 |

**核心改动：引入「批次」作为调度单位。** 一个批次 = 一组内聚需求 + 一个验证组 + 一次完整 Loop。

---

## 二、批次划分

### 2.1 怎么切

按**子系统 / 层**切，不按时间切。判据是「能不能独立验收」：

| 项目类型 | 批次骨架 |
|:--|:--|
| Web 全栈 | 0 契约（API schema 冻结）→ A 数据层 → B 业务层 → C API 层 → D 前端 → E 集成 |
| 数据平台 | 0 契约（Schema）→ A 采集 → B 清洗 → C 计算 → D 存储 → E 调度 → F 监控 |
| 嵌入式 | 0 契约（寄存器/协议）→ A 驱动 → B 中间件 → C 应用 → D 功耗/实时性 |
| CLI 工具 | 0 契约（命令/退出码）→ A 核心逻辑 → B I/O → C 配置 → D 交互 |

**批次 0 永远是契约**：API 签名 / 数据 schema / 错误码 / 模块边界。它先冻结，后面所有批次都不许改它——改了就是所有下游批次一起返工。

### 2.2 批次表（放 `docs/loopforge/batches.md`）

```markdown
| 批次 | 名称 | 验证组 runner | 需求范围 | 依赖批次 | 状态 |
|:--|:--|:--|:--|:--|:--|
| 0 | 契约 | run_contract | R-01~R-05 | — | ✅ 冻结 |
| A | 数据层 | run_data | R-06~R-20 | 0 | ✅ 完成 |
| B | 业务层 | run_core | R-21~R-45 | 0,A | 🔄 进行中 |
| C | API 层 | run_api | R-46~R-60 | 0,B | ⏸ 未开始 |
```

**依赖批次全绿才能开工。** 这条不能破——在没冻结的地基上开发，返工成本是指数的。

## 三、需求编号体系（上百条需求时）

单需求用 `R-01` 就够。`agents/srs-drafter.md` 示例用的是两位数（`R-01~R-299`），那是给单需求项目看的。**大型项目必须改用三位数，否则上百条必撞号**：

```
R-001 ~ R-099   契约与基础设施
R-100 ~ R-299   核心业务
R-300 ~ R-499   API / 接口
R-500 ~ R-699   前端 / 交互
R-700 ~ R-799   非功能（性能/安全/可靠性）
R-800 ~ R-899   运维 / 可观测
R-900 ~ R-999   兼容 / 迁移
```

**Stage 0 切换时同步改 `srs-drafter` 的编号格式示例**（两个文档不必完全一致，但 SKILL.md 编排时必须明确告诉 `srs-drafter` 用三位数）。

TC 编号跟着走：`TC-R042-003` = R-042 的第 3 个测试用例。

**SRS 拆分**：一个批次一份 SRS，`docs/loopforge/srs/batch-<X>-<名称>.md`。加一份 `docs/loopforge/srs/README.md` 做索引（哪个批次覆盖哪些 R 号）。

## 四、多批次状态管理

单需求用一张 `loop-status.md`。多批次要**一批一份**：

```
docs/
├── batches.md                    ← 批次总表（上面那张）
├── loop-status/
│   ├── batch-A.md                ← A 批次的 Loop 状态
│   ├── batch-B.md
│   └── batch-C.md
```

每份 `batch-X.md` 用 `SKILL.md` 里那张状态表模板（含 DISPATCH 块、连续不过计数、累计回退、震荡对、越权事件）。

**G5.6 判定要改**：`allowed:` 的白名单要加上本批次的状态文件：

```bash
git status --porcelain | cut -c4- \
  | awk -v ok="$ALLOWED" 'index($0,ok)!=1{print}' \
  | grep -v "^docs/loopforge/loop-status/batch-${BATCH}\.md$"
```

## 五、Runner 分层（全量跑太慢）

上百条需求时，每轮都跑全量测试是不可行的。三层：

| 层 | 跑什么 | 耗时目标 | 何时跑 |
|:--|:--|:--|:--|
| **smoke** | 每批 2~3 个核心用例 | < 30s | 每次 `impl-coder` 改完 |
| **batch** | 本批次全部用例 | < 5min | Stage 4 每轮 |
| **full** | 全部批次 + 契约回归 | 不限 | 批次收尾 + 交付前 |

对应 Goal 门：

| 门 | 跑哪层 |
|:--|:--|
| G3.1（本批测试全绿） | batch |
| **G3.7（跨批回归，新增）** | full —— 本批改动没有破坏已完成批次 |

**G3.7 是大型项目必加的门**。单需求项目不需要它，多批次没有它就会出现"A 批次绿了，做 B 的时候把 A 改挂了，没人发现"。

```
G3.7 | 跨批回归 | $FULL_TEST_CMD; echo $? | =0 | 回退本批 Stage 4 | 阻断
```

## 六、契约冻结（批次 0 的产物）

批次 0 交付后，产出一份 `docs/contract.md` + 一组契约测试。此后：

**任何批次都不许改契约。** 真要改，走变更流程（第七节）。

契约测试 `run_contract` 的特点：
- 秒级，无 I/O，无外部依赖
- 只验结构不验业务：函数签名、字典键、错误码枚举、API 路径与状态码
- **每个批次的每一轮都要跑**，且必须全绿

```
G0.4（新增）| 契约未破坏 | $CONTRACT_CMD; echo $? | =0 | 停止，回批次 0 评审 | 阻断
```

> 为什么单列一条门：契约破坏和普通测试失败性质不同。普通失败是"这批没做好"，契约失败是"你把地基改了，所有已完成批次的验收都作废了"。

## 七、需求变更（跨月项目必然发生）

单需求 Loop 假设需求不变。大型项目必须有变更流程：

```
变更请求
   ↓
[1] 影响分析：这条需求改动波及哪些批次？
   ├── 只影响未开工批次 → 改 SRS，正常走
   ├── 影响进行中批次   → 暂停该批次，回 Stage 1 重拷问增量部分
   └── 影响已完成批次   → ⚠️ 走下面的返工流程
   ↓
[2] 已完成批次返工
   - 该批次状态从 ✅ 改回 🔄
   - 依赖它的下游批次全部标记「待重验」
   - 重跑该批次 Stage 1→5
   - 下游批次只需重跑 G3.7 跨批回归（不用全走一遍）
   ↓
[3] 契约变更（最贵）
   - 冻结的契约要改 → 所有批次待重验
   - 必须人工评审批准，不能自动流程推进
```

**记在 `docs/loopforge/change-log.md`**：

```markdown
| 日期 | 变更 | 影响批次 | 处置 | 批准人 |
|:--|:--|:--|:--|:--|
| 2026-08-12 | R-042 分页改为游标 | B（进行中）, C（未开工） | B 回 Stage 1 增量拷问 | — |
```

## 八、跨会话恢复

跨月项目必然跨很多次会话，上下文一定会丢。**恢复靠文件，不靠记忆**：

新会话开始时，主 Claude 按顺序读：

```
1. docs/loopforge/batches.md          → 现在做到哪个批次
2. docs/loopforge/loop-status/batch-<当前>.md → 该批次卡在哪个 Stage、哪个门、第几轮
3. docs/loopforge/goal.md             → 门的定义（可能被裁剪过）
4. docs/loopforge/change-log.md       → 有没有未处理的变更
```

**这四份文件是唯一事实来源。** 主 Claude 说"我记得上次..."一律不作数。

对应加一条自查：

```
Stage 开始前：我读过这四份文件了吗？还是在凭上下文里的印象？
```

## 九、并行开发（多人 / 多 agent）

批次之间无依赖时可以并行。约束：

| 约束 | 原因 |
|:--|:--|
| 并行批次不共享 `IMPL_ROOT` 子目录 | 否则 G5.x 无法归因是谁改的 |
| 每批一个 git 分支 | 基线协议要求工作区可控 |
| 契约文件任何批次都不许改 | 见第六节 |
| 合并前必须跑 G3.7 跨批回归 | 分支各自绿不代表合起来绿 |

**不建议并行的情况**：团队第一次用这套流程、批次依赖关系没理清、契约还没冻结。先串行跑完 2~3 个批次，熟了再并行。

## 十、成本预估

诚实说明工作量，别低估：

| 阶段 | 一个批次的 Agent 调用次数（估） |
|:--|:--|
| Stage 1 拷问 | 1~2（含回退重拷问） |
| Stage 2 SRS | 1~2 |
| Stage 3 设计 | 1~2 |
| Stage 4 Loop | 6~15（test-author / test-runner / impl-coder 交替，每轮 3 次） |
| Stage 5 双轮审计 | 2~4 |
| gate-checker | 每 Stage 退出 1 次，约 6~8 |
| **合计** | **约 20~35 次** |

一个 8 批次的中型项目 ≈ 160~280 次 agent 调用。**这不便宜**。

### 什么时候该用轻量档

不是所有项目都值得全套。轻量档保留真正不可替代的部分：

| 保留 | 可省 |
|:--|:--|
| `docs/loopforge/goal.md`（哪怕只有 5 条门） | Stage 1 拷问（已有 PRD 时跳过） |
| test-author / test-runner / impl-coder 三分离 | G2.x 全族（设计质量交给自查） |
| G5.1 + G5.2 越权检测 | Round 2（Round 1 有 P0 才跑第二轮） |
| Stage 5 单轮审计 | 每阶段的 gate-checker（改为主 Claude 读自查报告） |
| G0.4 契约门（多批次时） | G3.5 类型门、G1.5 优先级门 |

轻量档一个批次 ≈ 7~10 次调用。

**判断标准**：这个批次出错的代价 > 多跑 20 次 agent 的成本吗？是 → 全套；否 → 轻量。

## 十一、启动检查清单

从零开始一个大型项目，按顺序：

```
□ 装套件（二选一）
    全局: bash scripts/install.sh  然后每项目 bash <套件>/scripts/loopforge-init.sh
    本地: bash <套件>/scripts/loopforge-init.sh --local
□ 跑 bash scripts/preflight.sh      ← 环境自检，0 阻断项才继续
□ /loopforge <你的模糊需求>              ← 首跑自动建 docs/loopforge/ 并从 <SKILL_DOCS>/goal-template.md
                                       复制出 docs/loopforge/goal.md，不用手工 cp
□ 填 goal.md 的 IMPL_ROOT / TEST_ROOT / TEST_CMD / RUNNER / TYPE_CMD
□ 裁剪 goal.md 的门（删不适用的，加项目专属的）
□ 加 G0.4 契约门 + G3.7 跨批回归门（多批次必加）
□ 写 docs/loopforge/batches.md 批次表 + 依赖关系
□ 确认 .gitignore 覆盖测试产物
□ Windows: git config core.autocrlf false（否则 G5.x 被换行符干扰）
□ 建 docs/loopforge/loop-status/ 目录
□ 跑批次 0（契约）→ 冻结
□ 按依赖顺序跑后续批次
```

> `<SKILL_DOCS>` = skill 安装目录下的 `docs/`（全局 `$HOME/.claude/skills/loopforge/docs/`，
> Windows PowerShell 下同一目录写作 `%USERPROFILE%\.claude\skills\loopforge\docs\`；
> 本地 `<项目>/.claude/skills/loopforge/docs/`）——**不是**你项目里的 `docs/`。

**第一个批次跑慢一点，把流程磨顺。** 门的判据、路径变量、runner 分层这些在真跑之前都是纸上谈兵，第一个批次就是用来暴露它们的。
