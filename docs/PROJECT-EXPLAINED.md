# 第一部分：这个项目到底是什么

## 1.1 它解决什么问题

你跟 AI 说："帮我做一个聊天 App。"

**没有这套东西时会发生什么**：

AI 立刻开始写代码。写着写着发现不知道要不要支持群聊，就自己拍板"先做单聊"。测试红了，AI 顺手把断言从 `assert rows == 100` 改成 `assert rows >= 0`，绿了。最后 AI 说"做完了"。你打开一看——功能缺一半，测试全绿但什么都没验证。

**三个根本问题**：

| 问题 | 表现 |
|:--|:--|
| **需求没问清就动手** | AI 替你做了 50 个你不知道的决定 |
| **写代码的人自己判分** | 测试红了，改测试比改代码容易 |
| **"完成"没有客观标准** | AI 说完成了就是完成了 |

**这套方案的三个对策**：

| 对策 | 怎么做 |
|:--|:--|
| **先问清楚再动手** | 专门有个 agent 只负责问你问题，问到你确认为止 |
| **写的人不判分** | 写代码的 agent **没有跑测试的工具**——它物理上看不到测试是红是绿 |
| **完成 = 通过机器检查** | 30+ 条判定命令，跑一遍全绿才算完成 |

## 1.2 核心概念：Goal 门

**门**（Goal Gate）= 一条可以用命令判定的检查。

举例，"SRS 每条需求都写了三个层级" 这条门长这样：

```bash
# 判定命令
awk '/^### R-/{if(n)printf "%s:%d ",n,c; n=$2;c=0}
     /\*\*(正常路径|边界条件|异常路径)\*\*/{c++}
     END{if(n)printf "%s:%d\n",n,c}' docs/srs/demo.md

# 输出：R-01:3 R-02:3
# 通过判据：每个 R-XX 后面的数字 ≥ 3
```

跑出来 `R-01:3 R-02:1` → R-02 只写了 1 个层级 → **FAIL** → 自动退回 Stage 2 重写。

**这就是"闭环"的意思**：不是走完流程就完事，是每一步都有机器判定，不过就退回去重做。

## 1.3 核心概念：职责隔离

九个 agent，每个只干一件事，且**工具受限**。

最关键的三条：

```
impl-coder（写实现代码）    工具: Read, Edit, Write, Grep, Glob
                            ↑ 注意没有 Bash

test-author（写测试代码）   工具: Read, Edit, Write, Grep, Glob
                            ↑ 也没有 Bash

goal-auditor（审计）        工具: Read, Grep, Glob
                            ↑ 既没 Bash 也没 Edit/Write
```

**为什么这样设计**：

- `impl-coder` 没有 Bash → **跑不了测试** → 看不到红绿 → 没有"改断言凑绿"的动机（它根本不知道哪个断言挡路）
- `test-author` 没有 Bash → 同理 → 断言强度只能由 SRS 决定，不能由"能不能过"决定
- `goal-auditor` 什么都改不了 → 不可能"顺手修一下再说没问题"

这不是靠提示词说"你不要作弊"，是**工具层面让它做不到**。

## 1.4 七个阶段

```
Stage 0    定门        ← 确定"什么叫完成"
Stage 0.5  目标书      ← AI 问你问题，直到项目分解清楚
Stage 1    拷问        ← 6 维度深挖需求细节
Stage 2    SRS         ← 变成结构化需求文档
Stage 3    设计        ← 变成可直接照着写代码的设计
Stage 4    Loop        ← 写测试 ↔ 跑测试 ↔ 写实现，循环到全绿
Stage 5    审计        ← 两轮独立审计，第二轮不许看第一轮结论
```

每两个阶段之间都有门。不过 → 自动退回。

## 2.2 skills/loopforge/SKILL.md —— 大脑

**这是最重要的一个文件。** 整套流程的编排手册。

**谁读它**：主 Claude（你在对话框里说话的那个 AI）

**里面有什么**：

| 内容 | 作用 |
|:--|:--|
| 9 角色分工表 | 谁能写什么、谁能跑什么 |
| 7 阶段流程图 | 从哪走到哪，不过怎么退 |
| **12 个 agent 调用模板** | 每个阶段怎么派人，prompt 写什么 |
| Stage 4 三方交替内循环 | 写测试 → 跑测试 → 写代码的具体转法 |
| 主 Claude 路由规则表 | 收到 9 种不同报告分别派谁 |
| 派工基线协议 | 派人干活前必须做的三步 |
| 防死循环规则 | 转不出去怎么办 |
| 状态表模板 | loop-status.md 长什么样 |

**举一个调用模板的实例**：

```
Agent(
    description="补实现",
    prompt="读 docs/design/<需求名>.md。按以下缺口清单补实现，
            只能写 $IMPL_ROOT：
            <test-runner 报告的 [GAP]/[FAIL] 原文摘录>
            设计文档没定义的行为不要自己发明，返回 [设计缺口]。",
    subagent_type="impl-coder"
)
```

注意 `<test-runner 报告的原文摘录>` —— 传给 impl-coder 的是**事实原文**，不是"我觉得是这里有问题"。传结论会带偏它的判断。

**路由规则表**（主 Claude 收到报告后派谁）：

| 报告内容 | 根本原因 | 派给 |
|:--|:--|:--|
| `[GAP]` 功能缺口 | 实现没写 | `impl-coder` |
| `[FAIL]` 新 Bug | 实现有错 | `impl-coder` |
| `⚠️ 弱断言` | 测试断言不够强 | `test-author` |
| `⚠️ 可疑 skip` | 测试用跳过掩盖 | `test-author` |
| `[设计缺口]` | 设计文档没定义 | 退回 Stage 3 |
| `[需求缺口]` | SRS 没这条 | 退回 Stage 2 |
| `[无法判定]` | **判定命令本身跑不动** | 退回 Stage 0 修门 |

最后一行很关键。命令跑不动就是门写错了，重跑一万次 agent 也没用。

## 2.3 agents/ —— 九个干活的

### ① goal-architect.md —— 项目目标架构师

**阶段**：0.5
**工具**：Read, Write, Grep, Glob（无 Bash）
**只能写**：`docs/goal-doc*.md`

**它是唯一直接跟你对话的 agent。**

**干什么**：你说"做一个微信"，它把这句话变成一份能驱动后面所有阶段的项目分解文档。

**工作方式**——多轮问答，不是一次性输出：

```
第 1 轮：
  它写一版 goal-doc（允许大量"待确认"标记）
  返回问题清单给你：

  🔴 必答（影响项目能否开始）
  Q1: 核心用户群是？（我猜：普通消费者，10 万级）
  Q2: 第一个里程碑交付什么？（我猜：单聊 + 群聊）

  🟡 待澄清（可暂缓）
  Q3: 多端一次到位吗？
  Q4: 离线消息要吗？

你回答："Q1 对，Q2 只做单聊，Q3 先做移动端，Q4 要"

第 2 轮：
  它改 goal-doc，重新算还剩哪些没问清
  返回新的问题清单

... 循环 ...

直到你说"确认，下一阶段"
```

**关键约束**：

| 禁止 | 为什么 |
|:--|:--|
| 替你做技术决策 | 它的产出是**你的决策记录**，不是它的主张 |
| 跳过你的审查 | 没你点头不能进 Stage 1 |
| 你答含糊就自己猜 | 你说"差不多就行"，它必须追问具体值 |

**你说一句话它也能出初版**：哪怕你只说"做一个微信"，它也会把 7 个章节全填上"最合理猜测 + 显式标注[待确认]"——不会让你对着空白发呆。

### ② req-interrogator.md —— 需求拷问官

**阶段**：1
**工具**：Read, Write, Grep, Glob（无 Bash）
**只能写**：`docs/srs-raw/`

**干什么**：goal-doc 定了大方向，它负责挖细节。**6 个维度，一个都不能少**：

**维度 1 — 5W2H**（基本盘）

| W | 问什么 | 实例 |
|:--|:--|:--|
| What | 做什么 | "用户上传 CSV 后要看到什么？图表长什么样？" |
| Why | 为什么做 | "替代什么现有方案？" |
| Who | 谁用 | "销售？分析师？所有人？" |
| When | 何时用/多频繁 | "每天一次还是每小时 100 次？" |
| Where | 在哪跑 | "Web？桌面？移动？云？本地？" |
| How | 怎么用 | "几步完成？要登录吗？" |
| How much | 花多少 | "性能预算？钱预算？" |

**维度 2 — 边界条件**

输入边界（最大/最小/空/特殊字符——CSV 含 BOM？空行？中文路径？百万行？）、输出边界（精度/单位/格式/小数位/编码）、状态边界（首次使用？中途取消？网络断？）、时间边界（时区？夏令时？跨年？）

**维度 3 — 异常路径**

输入异常（坏数据 → 报错？降级？跳过？）、环境异常（网络断/磁盘满/第三方挂/权限不足）、并发异常（多用户同时操作？重复提交？）、版本异常（新旧数据兼容？）

**维度 4 — 非功能需求**

性能（P99/吞吐/并发）、可靠性（可用性 99.9%？恢复时间？）、安全（认证/授权/加密/审计）、可维护性（日志/监控/告警）、可观测性（埋点/链路追踪）、合规（GDPR/等保）

**维度 5 — 隐性需求**（你没说但通常要）

向后兼容、易用性、可扩展性、国际化、数据治理（保留多久？删除策略？备份？）、培训运维

**维度 6 — 冲突点**

需求间冲突（"极简" vs "功能全"？"快" vs "安全"？）、与存量冲突、与组织冲突（技术栈/规范/资源/时间）

**产出**：`docs/srs-raw/<需求名>-interrogation.md` —— 一份待你答的问卷。

**对应的门**：
- G0.1 六维度齐全且每维度非空
- G0.2 无未决项（不能有"待定/TBD"）
- G0.3 冲突已裁决（冲突表每行都有裁决）

### ③ srs-drafter.md —— SRS 起草官

**阶段**：2
**工具**：Read, Write, Grep, Glob（无 Bash）
**只能写**：`docs/srs/`

**干什么**：把你答完的问卷变成结构化需求文档。

**编号规则**：

```
R-01 ~ R-99     功能需求
R-100 ~ R-199   非功能需求（性能/可靠性/安全/可维护性）
R-200 ~ R-299   约束（兼容性/依赖/法规/时间）
```

大项目改用三位数（`R-001~R-999`），否则上百条必撞号。

**每条需求必须写三层级**：

| 层级 | 内容 |
|:--|:--|
| 正常路径 | 主流程，预期输入 → 预期输出 |
| 边界条件 | 极值/特殊输入 |
| 异常路径 | 失败情况 + 降级策略 |

**验收口径必须可机读**——这是铁律：

```
❌ 错：性能良好
❌ 错：用户体验流畅
❌ 错：代码质量高

✅ 对：P99 < 200ms（wrk 压测 100 并发 30s，95th < 200ms）
✅ 对：传 100MB CSV < 5s（run_bench.py --size=100MB → assert elapsed < 5）
✅ 对：传非法 CSV → exit code != 0 且 stderr 含 "INVALID_CSV"
```

**为什么必须可机读**：Stage 4 的 test-author 要把这句话直接翻译成 `assert`。写"性能良好"，它翻译不出来。

**还要写验收矩阵**（哪条需求由哪个测试覆盖）：

| R-XX | 验证方式 | TC 编号 | 自动化 |
|:--|:--|:--|:--|
| R-01 | 单元测试 | TC-R01-001 | ✅ |
| R-01 | 集成测试 | TC-R01-002 | ✅ |

**纯度要求**：SRS 里不许出现"待定/已确认/已实现/讨论中"这类状态词，也不许出现代码路径。SRS 是源头，必须干净。

**对应的门**：G1.1（三层级齐）· G1.2（验收口径有命令块）· G1.3（验收矩阵无遗漏）· G1.4（纯度）· G1.5（优先级）

### ④ design-author.md —— 设计作者

**阶段**：3
**工具**：Read, Write, Grep, Glob（无 Bash）
**只能写**：`docs/design/`

**干什么**：SRS 说"要什么"，设计说"怎么做"。

**产出六个章节**：

```
1. 架构        模块划分 / 数据流 / 依赖方向（禁循环）
2. 接口定义    每个接口的完整签名 + 类型
3. 行为边界    逐条 R-XX：实现策略 / 正常路径 / 边界处理 / 不做什么
4. 错误处理    错误码表 + 重试策略 + 降级策略
5. 验收口径    逐条 R-XX 的验证命令 + 预期
6. 风险与权衡  选了什么、放弃了什么、为什么
```

**接口定义要给完整签名**：

| 接口 | 签名 | 输入约束 | 返回 | 错误 |
|:--|:--|:--|:--|:--|
| 上传解析 | `parse_csv(path: str, encoding: str = "utf-8") -> DataFrame` | path 存在且可读 | 行数 ≥ 0 | `EncodingError` / `EmptyFileError` |

**关键约束**：**SRS 没定义的东西不许自己发明**。缺了就返回 `[需求缺口]`，让主 Claude 退回 Stage 2。

**为什么不让主 Claude 直接写设计**：主 Claude 上下文里塞满了前面所有对话，写出来的设计会隐含"我知道后面怎么实现"的假设，反而漏掉显式定义。交给上下文干净的 design-author。

### ⑤ impl-coder.md —— 实现者

**阶段**：4
**工具**：Read, Edit, Write, Grep, Glob（**无 Bash**）
**只能写**：`$IMPL_ROOT`（通常 `src/`）

**干什么**：按设计文档写代码。

**它看不到测试是红是绿。这是故意的。**

**红线**：

| 禁止 | 为什么 |
|:--|:--|
| 写 `tests/` 下任何文件 | 你不知道测试红绿，改测试只可能是凑绿 |
| 改测试断言 / 加 skip / 调容差 | 假绿的头号来源 |
| 改 SRS 或设计文档 | 那是你的输入，不是产物 |
| 改 `KNOWN_FAILURES` | 那是 runner 的登记表 |

**输入给它的是事实报告**：

```
[GAP] 功能缺口：编码校验未实现 ← 涉及测试 test_R02_encoding ← 设计文档 §3.1
[FAIL] 新 Bug：空数据崩溃 ← 涉及测试 test_R03_chart:42
```

不是"我觉得是数据没传进来"。归因由它自己做。

**五个反模式**（审计会抓）：

| 反模式 | 长什么样 | 为什么禁 |
|:--|:--|:--|
| 配置回显 | `return config.value` 冒充"计算结果" | 值对但来源错，比算错更隐蔽 |
| 绕过实现层 | 编排层内联重写算法，不调已有模块 | 模块单测绿，端到端是另一套逻辑 |
| 数据丢弃 | 上游算好的数据在下游被丢掉 | 沉默失效 |
| 两套实现 | 简单模式单独写一份 | 两份逻辑必然发散 |
| stub 交差 | `raise NotImplementedError` 当实现了 | 直接判 P0 |

### ⑥ test-author.md —— 测试作者

**阶段**：4
**工具**：Read, Edit, Write, Grep, Glob（**无 Bash**）
**只能写**：`$TEST_ROOT` + `docs/verification/`

**干什么**：把 SRS 的验收口径翻译成测试代码。

**它也看不到红绿。** 看不到红绿 → 没有"调断言凑绿"的动机 → 断言强度只由 SRS 决定。

**翻译规则**：

| SRS 字段 | → 测试代码 |
|:--|:--|
| 验收口径的命令 | `subprocess.run([...])` |
| 验收口径的预期 | `assert` 语句 |
| **预期含数值指标** | **必须生成数值断言**，禁止只写 `returncode == 0` |
| 层级=异常 | `pytest.raises` 或 `assert returncode != 0` |

**功能没实现怎么办**——铁律：**写会失败的测试，不许 skip**

```python
# ❌ 错：功能没实现就跳过
@pytest.mark.skip(reason="校验功能未实现")
def test_validate_encoding(self): ...

# ✅ 对：写预期行为的断言，让它红 → 缺口可见
def test_validate_encoding(self):
    result = subprocess.run([..., 'fixtures/gbk.csv'], capture_output=True)
    assert result.returncode != 0        # 当前会失败 → [GAP] 暴露出来
    assert 'ENCODING' in result.stderr
```

**只有四种情况可以 skip**：需人工判断的（UI 美观度）、依赖已删除且有其他覆盖、极慢（分钟级）、外部工具没装。

**最重要的一条红线 —— 不许往 `KNOWN_FAILURES` 加东西**：

这个列表是全套件**唯一能让红测试合法变绿**的通道。登记进去 → 标 `[WARN]` → 不阻止验收 → runner 退出码仍是 0 → 门判 PASS。而 runner 由 test-author 独占写权。

所以有专门一条门 **G3.6 查 `KNOWN_FAILURES` 必须为空**（阻断级），审计员的自查清单里也有一条。加进去会被抓到，本轮作废。

### ⑦ test-runner.md —— 测试执行者

**阶段**：4
**工具**：Read, **Bash**, Grep, Glob（**无 Edit/Write**）

**干什么**：跑测试，报事实。

**六步**：
1. 跑 runner（全量 / quick）
2. 跑回归
3. skip 审计（扫所有 skip，分"合理"和"可疑"）
4. 断言强度审计（找只验 `returncode == 0` 的测试，对照 SRS 看是否漏了数值断言）
5. 类型检查（如果项目配了）
6. 返回事实报告

**报告纪律**：

| 要求 | 正例 | 反例 |
|:--|:--|:--|
| 只报事实 | "stderr: `KeyError: 'data'`，位置 chart.py:88" | "应该是数据没传进来" |
| 给可定位信息 | 文件:行号 + 断言原文 + 实际值 | "有几个测试挂了" |
| 不预判严重性 | 按客观规则分类 FAIL/GAP/WARN | "这个问题不大" |
| 不建议修法 | 不写 | "建议在 parser 加个判空" |

**为什么不让它做归因**：归因会带偏修复方向。它给的原始事实越干净，主 Claude 和 impl-coder 的判断越不容易被误导。

**它有 Bash，所以有个已知缺口**（后面 §2.4.3 详说）。

---

### ⑧ gate-checker.md —— 门判定员

**阶段**：全阶段（每个阶段退出都跑）
**工具**：Read, **Bash**, Grep, Glob

**干什么**：按 `docs/goal.md` 里写死的判定命令逐条跑，报 PASS/FAIL。

**它是机械执行器，不是审计员**：

| | gate-checker | goal-auditor |
|:--|:--|:--|
| 性质 | 机械判定 | 判断性审计 |
| 依据 | goal.md 里写死的命令 | 审计维度 + 自己的判断 |
| 工具 | 有 Bash | **无 Bash** |
| 频率 | 每阶段退出 | 只在 Stage 5 |
| 能说"虽然 FAIL 但没关系"吗 | ❌ 不能 | ✅ 可以（带论证） |

**为什么拆成两个 agent**：自检若由终审同一角色做，自检时形成的"这没问题"印象会污染终审。机械判定不产生印象。

**三种结果**：

| 结果 | 条件 |
|:--|:--|
| ✅ PASS | 命令跑通 + 输出满足判据 |
| ❌ FAIL | 命令跑通 + 输出不满足判据 |
| ⚠️ 无法判定 | 命令报错/文件缺失/**输出为空但判据要求数值** → **不算 PASS** |

**"无法判定绝不能当 PASS"** —— 这条守住，Loop 才不会靠"检查失败=默认通过"混过去。

**它还负责越权检测**（G5.x）：

```bash
git status --porcelain | cut -c4-    # 列出本轮 agent 的全部改动
```

| 本轮派了谁 | 只允许动 | 越权信号 |
|:--|:--|:--|
| impl-coder | `src/**` | 出现 `tests/**` → 🔴 |
| test-author | `tests/**` | 出现 `src/**` → 🔴 |
| test-runner | 无（应零改动） | 任何改动 → 🔴 |
| goal-auditor | `docs/audit/**` | 出现代码 → 🔴 |

越权 → 本轮结果作废 → 回滚 → 重派。

---

### ⑨ goal-auditor.md —— 独立审计员

**阶段**：5
**工具**：Read, Grep, Glob（**无 Bash 无 Edit 无 Write**）

**干什么**：独立判断这份交付能不能过。

**五个维度**：

| 维度 | 查什么 |
|:--|:--|
| **A 功能完整性** | 每条需求真实现了吗？有 TODO/stub 吗？有 mock 顶替吗？ |
| **B 测试方案** | 每条需求有测试吗？三层级齐吗？数值指标进断言了吗？ |
| **C 测试真绿性** | **主战场** —— 绿得可疑吗？ |
| **D 覆盖矩阵** | 验收矩阵 100% 覆盖吗？ |
| **E 红线合规** | 编排绕过实现了吗？有越权事件吗？ |

**"绿得可疑"抽查法**（至少做 3 处）：

1. 挑一个通过的测试，把断言在脑子里改成明显错误的值——**原断言真的会挂吗？**
2. 断言的期望值，在 SRS 或设计文档里**能找到出处吗**？找不到 = 可能是从实现输出回抄的
3. 测试有没有可能"因为功能没跑到"而通过（提前 return / 异常被吞）？

**重点反模式 —— 配置回显**：

```
对每个带数值的验收指标，追问："这个值由哪个函数算出？"
答案是 config 字段或内联常量 → 🔴 P0
```

配置回显最阴险的地方：值恰好等于配置值，所有"配置回代型"测试都会通过。

**双轮机制**：

| 轮 | 输入 | 特殊纪律 |
|:--|:--|:--|
| Round 1 | 全部产物 | 无 |
| **Round 2** | 全部产物（已修复版） | **禁读 Round 1 报告、修复记录、loop-status** |
| Round 3 | 同上 | 禁读 Round 1/2 的一切 |

**Round 2 为什么不能读 Round 1**：读了就会变成"检查 Round 1 提的都改了吗"，而不是"这份交付合格吗"。Round 1 漏掉的 P0，只有独立重审才可能被发现。

**它诚实承认这条是纪律级不是强制级**：它有 Read 工具，harness 拦不住它读那几个文件。唯一保障是它自己遵守 + 报告里"本轮未读取任何前轮结论"的声明。文档里明说：**读了却声明没读，整个双轮机制就是摆设——那还不如老实说读了**。

### ③ role-permission-matrix.md —— 职责隔离契约

**九个角色的权限矩阵 + 四层防线。**

**最有价值的部分是它诚实承认的一个缺口**：

> ### ⚠️ 必须承认的一条：Bash ⊇ Write
>
> **"无 Edit/Write → 改不了代码"这句话是错的。**
>
> 持有 Bash 的 agent（`test-runner`、`gate-checker`）可以用 `>` 重定向、`python -c`、`perl -pi`、`patch`、`git apply` 写入任意文件。而它们**同时能跑测试** —— 这意味着单个 agent 在原理上就能独立闭合「改被测物 → 跑测试 → 报告结果」全回路。

| 防线 | 对 Bash 写入是否有效 |
|:--|:--|
| L1 `tools:` 白名单 | ❌ 无效——Bash 就是被授予的工具 |
| L2 `settings.json` deny | ⚠️ 部分——挡得住命令名，**挡不住 shell 重定向**（`>` 是语法不是命令） |
| L3 文档红线条款 | ⚠️ 靠自觉 |
| L4 **G5.x git 事后检测** | ✅ **有效**——不管用什么手段写的，`git status` 都看得见 |

**结论：对这两个角色，L4 是唯一真防线。**

文档明说：**不要在对外材料里宣称"改不了代码"** —— 准确表述是"改了会被 G5.x 抓到并作废重跑"。

**同样诚实的第二条**：主 Claude 的收权是**纪律级不是强制级**。没有任何机制能硬性限制主线程的工具（Skill 的 `disallowed-tools` 是回合级，`settings.json` 是会话全局会连累 subagent）。真防线是 G5.6 事后比对派工记录。

### ⑤ loop-status-spec.md —— 状态文件规范

`docs/loop-status.md` 是 Loop 的**唯一状态来源**。上下文会压缩、会话会断，这份文件不会。

**DISPATCH 块**（机读，G5.6 的输入）：

```
<!-- DISPATCH -->
round: 4-3
agent: impl-coder
allowed: src/
<!-- /DISPATCH -->
```

**顺序铁律**：先写 DISPATCH → `git commit` 打基线 → 再派 agent。**颠倒 = 主 Claude 自己的状态改动被算进 agent 越权 = 活锁**。

**三个计数器**：

| 计数器 | 阈值 | 触发 | 归零条件 |
|:--|:--:|:--|:--|
| 门连续不过 | 3 | 停自动回退，升级给人 | 该门转 PASS |
| 累计回退 | 10 | 回 Stage 0 复审门定义 | **不归零** |
| 震荡对交替 | 3 | 标门冲突，回 Stage 0 | 裁决后 |

**为什么必须落盘**：主 Claude 的上下文会被压缩，压缩后"这个门已经连续挂了 2 轮"这个事实就消失了——三条防死循环规则全部失去存储，等于没有。

### ⑥ large-project-guide.md —— 大项目指南

单需求 Loop 撑不住上百条需求、跨月、多人的项目。

**核心改动：引入「批次」作为调度单位。**

| 批次 | 内容 | 依赖 |
|:--|:--|:--|
| **0 契约** | API schema / 错误码 / 模块边界 | — |
| A | 数据层 | 0 |
| B | 业务层 | 0, A |

**批次 0 永远是契约，冻结后所有批次不许改。** 改了 = 所有下游批次一起返工。

**Runner 分层**（全量跑不动）：

| 层 | 跑什么 | 耗时目标 | 何时跑 |
|:--|:--|:--|:--|
| smoke | 每批 2~3 个核心用例 | < 30s | 每次改完 |
| batch | 本批全部用例 | < 5min | Stage 4 每轮 |
| full | 全部批次 + 契约回归 | 不限 | 批次收尾 |

**成本预估**（诚实说明，不低估）：

| 阶段 | Agent 调用次数 |
|:--|:--|
| Stage 1 拷问 | 1~2 |
| Stage 2 SRS | 1~2 |
| Stage 3 设计 | 1~2 |
| Stage 4 Loop | 6~15 |
| Stage 5 审计 | 2~4 |
| gate-checker | 6~8 |
| **一个批次合计** | **约 20~35 次** |

8 批次的中型项目 ≈ 160~280 次调用。**这不便宜。**

所以还给了**轻量档**：保留 goal.md + 三分离 + G5.1/G5.2 越权检测 + 单轮审计，省掉 Stage 1 拷问（有 PRD 时）、G2.x 全族、Round 2。一个批次 ≈ 7~10 次调用。

判断标准：**这个批次出错的代价 > 多跑 20 次 agent 的成本吗？**

## 2.6 scripts/ —— 六个脚本

### ① install.sh / install.ps1 —— 全局层安装

装 skill + 9 agent + 3 份驱动文档到 `~/.claude/`。

**校验**：源目录存在 → 9 个 agent → 5 个命令 → 装完再逐个确认 9 个 agent 都到位。

**幂等**：先 `rm -rf` 旧 skill 目录再拷，避免残留过期文件。

**不动** `~/.claude/commands/`、`CLAUDE.md`、`settings.json`——不覆盖 Claude Code 原生任何东西。

**为什么要逐个数而不是数目标目录总数**：用户 `~/.claude/agents/` 里通常已有别的 agent。数总数的话，装漏了也会被无关 agent 撑成"看着对"。

`.ps1` 是 Windows 无 Git Bash 时的等价版本，行为与 `.sh` 一致。

### ② loopforge-init.sh / loopforge-init.ps1 —— 项目级注册

装 5 个命令到 `<项目>/.claude/commands/`。

**校验**：commands 目录存在 → 5 个文件 → **逐个查 frontmatter 合法**（首个非空行是 `---` 且含 `name:` 行）→ 全局层已装 → 装完逐个确认到位。

**CRLF 容错**（修过的地方）：

```bash
FIRST_LINE=$(grep -m1 -v '^[[:space:]]*$' "$f" | tr -d '\r' || true)
```

不加 `tr -d '\r'`，在保留 CR 的环境下合法文件会被判"frontmatter 损坏"——**装不上，且报错误导**。

### ③ preflight.sh —— 环境自检

8 段检查：平台识别 / shell / 必需命令 / 工具方言（GNU vs BSD）/ 非常备命令 / git 状态 / **路径变量** / 判据冒烟测试。

**第 7 段最关键**——检测 Maven 布局的致命组合：

```bash
case "$TEST" in
  "$IMPL"*) bad "TEST_ROOT 以 IMPL_ROOT 开头（Maven 布局？）
                 —— G5.1 恒判 0 = 永远绿灯" ;;
esac
```

Java/Maven 项目实现在 `src/main/java`、测试在 `src/test/java`，**都在 `src/` 下**。沿用默认值 → `impl-coder` 改测试凑绿时 G5.1 恒为 0 → **永远绿灯**。失效方式是静默放行不是报错。

**这条检查自己也曾有 CRLF bug**（修过的地方）：CR 留在提取出的路径里，`src/test/\r` 不以 `src/\r` 开头 → **拦截器自己漏判** → 用户拿到干净 preflight + 永久绿灯的 G5.1。这类"检查器自身失效"最难发现。

### ④ validate_suite.py —— 套件自校验

**套件是规格集不是代码，但设计本身可以测。**

六层，107 项：

| 层 | 查什么 | 例 |
|:--|:--|:--|
| L1 结构完整性 | 文件齐、frontmatter 合法 | 9 agent 齐吗？5 命令齐吗？双版脚本齐吗？ |
| L2 **权限不变式** | 职责隔离硬约束是否成立 | 写者持有 Bash 吗？审计者能写吗？ |
| L3 引用一致性 | 跨文档引用可解析 | 有门要 gate-checker 调它没有的工具吗？ |
| L4 闭环完整性 | 每门有回退、防死循环规则齐 | G5.x 越权门存在吗？ |
| L5 契约一致性 | 矩阵声明 vs 实际 frontmatter | 说的和写的一致吗？ |
| L6 **门命令实跑** | 造样例真跑判定命令 + 已修 bug 回归 | 清空验收矩阵，G1.3 真能判 FAIL 吗？ |

**L6 是后加的，因为 L1~L5 只查文档结构、从不执行门命令** —— 四个 bug 藏在这个盲区里。

**L2 的判据被独立审计推翻过一次**：原来写的是"写者/执行者/审计者三集合互不相交"，审计员穷举 7 种工具的全部 128 个子集证明它**恒真**——不管 frontmatter 怎么写都 PASS，零证据价值。现改为逐角色断言。

# 第三部分：完整工作流程

## 3.1 装（两步，一次性）

```bash
# 第一步：全局（所有项目共用）
cd <loopforge 目录>
bash scripts/install.sh
# Windows 无 bash: powershell -NoProfile -ExecutionPolicy Bypass -File scripts\install.ps1

# 第二步：项目（每个项目一次）
cd <你的项目>
git init                                       # 必须，G5.x 靠 git
bash <套件路径>/scripts/loopforge-init.sh
bash scripts/preflight.sh                      # 0 阻断才继续
```

Windows 额外一步：`git config core.autocrlf false`

## 3.2 Stage 0.5 —— 你唯一需要动脑的阶段

```
你：/loopforge 我要做一个微信这样的聊天 App
   │
   ├─ 主 Claude 初始化 docs/ 目录、复制门模板
   ├─ 主 Claude 读 SKILL.md
   └─ 主 Claude 派 goal-architect
        │
        ├─ 读 goal-doc-template.md
        ├─ 写初版 docs/goal-doc.md（七章节 + 大量[待确认]）
        └─ 返回问题清单

主 Claude 呈现给你：
   🔴 必答
   Q1: 核心用户群？（我猜：普通消费者 10 万级）
   Q2: 第一个里程碑？（我猜：单聊+群聊）
   🟡 待澄清
   Q3: 多端一次到位吗？
   Q4: 离线消息要吗？

你：Q1 对，Q2 只做单聊，Q3 先移动端，Q4 要
   │
   └─ 主 Claude 再派 goal-architect 修订
        └─ 返回新的（更短的）问题清单

... 循环 2~4 轮 ...

你：确认，下一阶段
   │
   └─ gate-checker 判 G0.5/G0.6/G0.7
        ├─ 七章节齐吗？
        ├─ 范围外写了吗？
        └─ [待确认] ≤ 3 吗？

   全绿 → 进 Stage 1
```

**这个阶段花的时间最值**。这里想清楚一小时，后面省十小时返工。

## 3.3 Stage 1~3 —— 需求到设计（基本自动）

```
Stage 1  req-interrogator
   │  读 goal-doc §2 子系统划分
   │  按 6 维度对每个子系统拷问
   └─ 产出 docs/srs-raw/<子系统>-interrogation.md（一份问卷）

   你答问卷（这是第二次需要你参与）

   gate-checker 判 G0.1~G0.3
   不过 → 退回 Stage 1 补拷问

Stage 2  srs-drafter
   │  读拷问清单 + 你的答卷
   │  拆条编号 R-01~R-XX
   │  每条写三层级 + 可机读验收口径
   └─ 产出 docs/srs/<需求名>.md

   gate-checker 判 G1.1~G1.5
   不过 → 退回 Stage 2（根因在答卷 → 退到 Stage 1）

Stage 3  design-author
   │  读 SRS（唯一权威输入）
   │  写架构/接口/行为边界/错误处理/验收口径/风险
   └─ 产出 docs/design/<需求名>.md

   gate-checker 判 G2.1~G2.5
   不过 → 退回 Stage 3（根因在 SRS → 退到 Stage 2）
```

## 3.4 Stage 4 —— 核心内循环

**这是职责隔离真正发挥作用的地方。**

```
每次派人干活前，主 Claude 必做三步（顺序不可颠倒）：
   1. 写 docs/loop-status.md 的 DISPATCH 块
   2. git add -A && git commit -m "pre-dispatch: test-author round 4-1"
   3. 派 agent

────────────────────────────────────────

[1] test-author 写测试
      读 SRS + 设计
      每条 R-XX 生成正常/边界/异常三层测试
      功能没实现 → 写会失败的断言（不许 skip）
      ↓ 它没有 Bash，交不出运行结果

[2] test-runner 跑测试
      跑 runner + 回归 + skip 审计 + 断言强度审计
      产出事实报告：
         [FAIL] test_R03_chart::test_empty
                tests/test_R03_chart.py:42
                断言 assert 'chart' in out
                实际 stdout 为空，stderr: KeyError: 'data'
         [GAP]  test_R02_encoding::test_gbk 编码校验未实现
         ⚠️ 弱断言 tests/test_R01.py:30 只有 returncode==0
      ↓ 它没有 Edit/Write，改不了任何东西

[3] 主 Claude 读报告 → 只做路由（不自己修）
      ├─ [GAP]/[FAIL] → 派 impl-coder → 回 [2]
      ├─ 弱断言/可疑 skip → 派 test-author → 回 [2]
      ├─ [设计缺口] → 退回 Stage 3
      └─ 全绿 → [5]

[4] impl-coder 补实现
      读设计文档 + 缺口清单原文
      只改 src/
      设计没定义的不许自己发明 → 返回 [设计缺口]
      ↓ 它没有 Bash，看不到自己改对没有

[5] gate-checker 判门
      G3.1 测试全 PASS      G5.1 impl-coder 没碰 tests/
      G3.2 零可疑 skip      G5.2 test-author 没碰 src/
      G3.3 零弱断言         G5.3 test-runner 零改动
      G3.5 类型不劣化       G5.6 改动范围与 allowed 一致
      G3.6 KNOWN_FAILURES 为空 ← 堵最大绿化通道

      越权 → 本轮作废 → 回滚 → 重派
      全过 → 出 Stage 4
```

**这个循环里每一环的"不可能性"**：

- test-author 想让测试变绿？**它没 Bash，看不到红绿**
- impl-coder 想改测试凑绿？**G5.1 git 检测会抓到，本轮作废**
- test-runner 想"顺手修一下"？没 Edit/Write——**但它有 Bash 能用 `>` 写文件，真防线是 G5.3**
- gate-checker 想放水？判定命令写死在 goal.md——**但它有 Bash 能改 goal.md，真防线是把 goal.md 纳入 G5.x 检测**

## 3.5 Stage 5 —— 双轮审计

```
Round 1  goal-auditor（fresh 实例）
   │  输入：SRS/设计/代码/测试/test-runner报告/门报告
   │  五维度 A~E，至少 3 处断言溯源抽查
   └─ 产出 P0/P1/P2 清单 + [AUDIT VERDICT] 结构化块

   主 Claude 派 impl-coder/test-author 修全部 P0/P1
   落盘 docs/audit/round1-fixes.md

   gate-checker 判 G4.2（逐条比对编号 vs 修复记录）

Round 2  goal-auditor（全新实例）
   │  🔴 prompt 里显式禁止读：
   │     docs/audit/goal-audit-round1-*.md
   │     docs/audit/round1-fixes.md
   │     docs/loop-status.md（有"下一步：派 X 修 Y"会泄漏）
   │  当作这个项目从没被审过，独立重审
   └─ 产出新的 P0/P1/P2

   gate-checker 判 G4.3（Round 2 的 P0+P1 == 0）
      注意：报告缺 [AUDIT VERDICT] 块 → 输出 "NOBLOCK" →
            按"无法判定"处理，不当 PASS

   不过 → 修 → Round 3（上限 3 轮）→ 仍有 → 升级给人
   全过 ��� ✅ 交付
```

## 3.6 防死循环

| 情况 | 检测方式 | 处理 |
|:--|:--|:--|
| 同一门连续 3 轮不过 | 读状态表计数 | 停自动回退，升级给人 |
| **两门交替失败** | 读震荡对表，同一对交替 ≥3 次 | 标门冲突，回 Stage 0 裁决 |
| 累计回退 > 10 次 | 读状态表计数 | 回 Stage 0 复审门是否过严/矛盾 |
| G5.x 检出越权 | gate-checker 报告 | 本轮作废 → 回滚 → 重派 |
| 同一 agent 二次越权 | 读越权事件表 | 停止，人工查 tools 是否真生效 |
| Round 3 仍有 P0 | G4.3 | 升级给人 |

**两条计数规则**（原设计没规定，规则层面可以永远转下去）：
1. 作废轮计入累计回退，**不计入**连续不过
2. 门从 FAIL 转 PASS 时该门连续不过归零；累计回退只增不减

## 3.7 跨会话恢复

上下文被压缩或会话断了，`/loopforge-resume` 按顺序读四份文件：

```
1. docs/goal-doc.md      项目目标（做什么）
2. docs/goal.md          门定义（怎么算完成）
3. docs/loop-status.md   当前进度（卡在哪）
4. docs/change-log.md    变更记录
```

**这四份文件是唯一事实来源。** 主 Claude 说"我记得上次..."一律不作数。

# 第四部分：建议

## 4.1 第一次别用大项目

```
/loopforge 我要做一个 TODO CLI
```

跑通一遍（约 20~35 次 agent 调用），流程就熟了。再上复杂项目。

## 4.2 你实际要做的只有三件事

1. **回答 goal-architect 的问题**（Stage 0.5，2~4 轮）
2. **答 req-interrogator 的问卷**（Stage 1，一次）
3. **看审计报告的 P0**（Stage 5）

其余全自动。

## 4.3 什么时候该用轻量档

| 保留 | 可省 |
|:--|:--|
| goal.md（哪怕只有 5 条门） | Stage 1 拷问（已有 PRD 时） |
| 三分离（写实现/写测试/跑测试） | G2.x 全族 |
| G5.1 + G5.2 越权检测 | Round 2（Round 1 有 P0 才跑） |
| Stage 5 单轮审计 | 每阶段 gate-checker |

判断标准：**这次出错的代价 > 多跑 20 次 agent 的成本吗？**

## 4.4 不适合用这套的场景

一次性脚本 / 玩具项目 / MVP 试错期（需求变太快）/ 纯主观审美类项目。

**这套东西的成本是真实的。** 它换来的是"完成"这个词有客观定义。值不值取决于你的项目。
